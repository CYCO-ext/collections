# Feature: fix-addres

Problem
-------
The Register microservice sends addresses through sync topics, but address payloads are not consistently ready to be stored as first-class MongoDB address documents.

Known issues:

1. Address IDs are not sent by the producer and must be generated by this service.
2. Street number is sent as a separate field and must be stored in the address collection.
3. Street, city, state, and number must be persisted in `collection_addresses`, not only in `address_cache`.
4. Latitude/longitude are often missing and must be enriched with ViaCEP + Nominatim when possible.
5. Duplicate addresses with the same normalized location key must not create duplicate documents.
6. The enrichment flow currently covers `addresses-sync`; `collector-sync` must also enrich and deduplicate its address before persisting collector data.

Goal
----
Provide one reliable address normalization, deduplication, persistence, and enrichment flow for all sync consumers that receive address data from Register.

The flow must create or reuse an Address document with normalized street, number, city, state, zipCode, coordinates, and enrichment metadata, then associate the resulting address ID with the incoming aggregate (`addresses-sync` address records and `collector-sync` collector records).

Constraints & Assumptions
------------------------

- Addresses originate in Brazil.
- `addresses-sync` and `collector-sync` both provide enough address data to attempt normalization and deduplication.
- `collector-sync` may contain the address embedded in the collector payload instead of a standalone address event.
- External geocoding uses ViaCEP for CEP-based normalization and OpenStreetMap Nominatim for coordinates.
- ViaCEP normalization is required when CEP is available; Nominatim is attempted only when coordinates are missing.
- If incoming latitude/longitude are already present, they are accepted and external geocoding is skipped.
- Address enrichment must be internal to sync consumption and must not require authenticated API calls.
- Respect external API rate limits and usage policies through caching, timeouts, configurable User-Agent, and fail-open behavior.

Acceptance Criteria
-------------------

AC-1: When an address is received from `addresses-sync` or `collector-sync` without an explicit ID, the service generates an address ID before persistence.

AC-2: Address entity includes and persists `street`, `number`, `city`, `state`, and `zipCode` in MongoDB `collection_addresses`.

AC-3: Before creating a new address document, the service normalizes the available address fields and checks for a duplicate by `(zipCode, street, number, city, state)`.

AC-4: If a duplicate address exists, the service reuses the existing address ID and does not create another `collection_addresses` document.

AC-5: If incoming latitude/longitude are present, the service persists them with enrichment source `provided` and skips Nominatim.

AC-6: If CEP is available and latitude/longitude are missing, the service calls ViaCEP first to normalize street/city/state, then checks cache, then calls Nominatim if no cached coordinates exist.

AC-7: If enrichment succeeds, the persisted Address includes latitude, longitude, enrichment status, enrichment source, and enrichment timestamp.

AC-8: If enrichment fails, the Address is still persisted with `ADDRESS_UNVERIFIED` status so retry/backfill can process it later.

AC-9: Enriched coordinates are cached in `address_cache` using a normalized key that includes CEP, street, number, city, and state.

AC-10: `collector-sync` persists or updates the collector with a reference to the enriched/reused Address ID produced by the shared address flow.

AC-11: `collector-sync` does not create duplicate address documents when multiple collectors share the same normalized address.

AC-12: The implementation includes tests proving that both `addresses-sync` and `collector-sync` invoke the shared enrichment/deduplication flow.

Traceability IDs
----------------

- FA-001: Generate ID if not provided by producer
- FA-002: Store street number in Address entity
- FA-003: Detect and deduplicate addresses by normalized key
- FA-004: Accept coordinates if present
- FA-005: Normalize address via ViaCEP when CEP is available
- FA-006: Geocode with Nominatim and attach lat/long
- FA-007: Cache enriched addresses
- FA-008: Mark unresolved addresses and expose retry path
- FA-009: Persist street, number, city, and state in `collection_addresses`
- FA-010: Enrich collector address from `collector-sync`
- FA-011: Link collector records to the reused or newly generated Address ID

Notes
-----

- Nominatim usage policy forbids heavy production usage of the public instance. Keep provider configuration explicit so production can switch to a paid provider or self-hosted Nominatim.
- The shared address flow should be idempotent: processing the same sync payload repeatedly must converge on the same address document or the same duplicate match.
